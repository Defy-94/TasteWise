# API 接口文档

所有接口由 `backend/` 提供，统一返回 JSON 格式：

```json
{ "code": 200, "msg": "ok", "data": { ... } }
```

- `code = 200` 成功；非 200 失败（常见：400 参数错误 / 401 未登录 / 404 不存在 / 409 状态冲突 / 429 触发限流 / 500 服务器错误）。
- **HTTP 状态码与 `code` 保持一致**：`code=404` 时 HTTP 状态码也是 404，不再一律返回 200。
  这样监控/告警能按状态码统计错误、反向代理与网关也能按状态码做缓存与重试策略。
  **响应体结构没有变**，所以前端读 `code` 的逻辑不受影响。
  > 若在某个客户端上发现业务错误被误判成「网络异常」，把
  > `backend/core/Response.php` 的 `$mirrorHttpStatus` 改为 `false` 即可恢复老行为（一律 200），
  > 前端无需改动。
- 支持 CORS，`OPTIONS` 预检请求由 `Response::handleOptions()` 自动处理。
- 前端封装见 `frontend/utils/api.ts`，请求体均为 `Content-Type: application/json` 的 JSON 字符串。
- **服务器内部错误的细节不会返回给外部调用方**：500 响应只带一句场景说明
  （如「下单失败」），完整细节（含 SQL 报错、文件路径）写入服务器错误日志。
  只有**本机回环地址**的请求才会拿到细节，方便本地调试。

## 鉴权说明（登录令牌）

除「免登录」接口外，所有涉及用户数据的接口都必须携带登录令牌。

### 1. 获取令牌

调用**微信一键登录**接口 `POST /api/user/login.php`，入参是小程序端 `wx.login()` 取得的临时 `code`：

```json
{ "code": "wx.login 返回的临时 code" }
```

返回的用户对象中会额外包含 `token` 字段：

```json
{
  "code": 200,
  "msg": "登录成功",
  "data": { "id": 10001, "openid": "...", "nickname": "...", "token": "eyJ1aWQiOjEwMDAxfQ.xxxx" }
}
```

### 2. 携带令牌

后续请求在请求头中携带（二选一，推荐第一种）：

```
token: <令牌>
```

```
Authorization: Bearer <令牌>
```

前端已统一处理：`frontend/utils/api.ts` 会自动把令牌加到每个请求头。

### 3. 令牌失效

令牌有效期 **7 天**。过期或非法时，后端返回：

```json
{ "code": 401, "msg": "未登录或登录已过期，请重新登录", "data": null }
```

前端收到 401 会自动清除本地登录态并跳转登录页。

### 4. 越权防护（重要）

**用户身份一律取自令牌，客户端传入的 `user_id` 会被完全忽略。**
因此无法通过修改请求参数查看、修改或删除他人数据（购物车、订单、个人资料）。
涉及具体资源的接口（如 `cart/remove.php`、`order/pay.php`）还会额外校验该资源是否属于当前用户。

> 令牌为 HMAC-SHA256 签名的自包含令牌，服务端不存储会话。
> 修改 `config/security.php` 中的 `token_secret` 会让所有已签发令牌立即失效。

## 订单状态与流转

订单状态定义（数据库 `orders.status`）：

| 状态值 | 含义 | 可执行操作 |
| --- | --- | --- |
| 0 | 待支付 | 去支付、取消订单 |
| 1 | 已支付 | 确认完成、取消订单 |
| 2 | 已完成 | 无（终态） |
| 3 | 已取消 | 无（终态） |

```
                  pay.php                complete.php
   [0 待支付] ───────────► [1 已支付] ─────────────► [2 已完成]
        │                        │
        └──────── cancel.php ────┘
                     ▼
              [3 已取消]（自动恢复库存）
```

- 所有状态流转都做了**前置状态校验**与**原子更新**（`UPDATE ... WHERE status = ?`），并发重复请求不会重复生效。
- 取消订单会把下单时扣减的库存**逐项恢复**，整个过程在事务内完成。
- 非法流转返回 `409`，例如对已支付订单再次调用 `pay.php`。
- **这三个接口都只是薄封装**：真正的状态机实现在 `core/OrderStatus.php`，
  接口只负责「鉴权 → 取参 → 调用 → 出参」。管理后台改订单状态调用的是同一个方法，
  因此不存在「后台和前台两套流转规则不一致」的问题。详见
  [architecture.md 第 5 节](architecture.md#5-订单状态流转)。
- 每个接口都会同时校验 `order_id` 与当前登录用户，操作他人订单统一返回 `404`
  （统一返回 `404`，避免通过响应差异判断订单号是否存在）。
- **待支付订单会超时自动取消**：下单时已扣库存，若不付款也不取消，
  那份库存就被永久占用了。因此待支付超过 `core/OrderExpiry.php` 的
  `TIMEOUT_MINUTES`（默认 15 分钟）的订单会被**自动取消并归还库存**，
  备注里追加「（超时未支付，系统自动取消）」。
  这是**懒清理**：在下单、查我的订单、后台看订单这些场景里顺手执行
  （phpstudy 没有可靠的 cron）。详见 [architecture.md](architecture.md) 第 12 节。

## 接口详情

### 1. 获取菜品分类

- **地址**：`GET /api/category/list.php`
- **入参**：无
- **返回 data**：
```json
[
  { "id": 1, "name": "热菜", "sort_order": 10, "icon_url": "" },
  { "id": 2, "name": "凉菜", "sort_order": 8,  "icon_url": "" }
]
```

### 2. 获取菜品列表（支持分类筛选与关键词搜索）

- **地址**：
  - `GET /api/dish/list.php` —— 全部
  - `GET /api/dish/list.php?category_id=1` —— 按分类
  - `GET /api/dish/list.php?keyword=汤` —— 按关键词搜索
  - `GET /api/dish/list.php?category_id=1&keyword=鸡` —— 两个条件**同时生效**
- **入参**：
  | 参数 | 必填 | 说明 |
  | --- | --- | --- |
  | `category_id` | 否 | 分类ID，不传或传 0 表示全部 |
  | `keyword` | 否 | 搜索关键词，**最长 20 字**（超长返回 `400`），同时匹配菜名与描述 |
- **返回 data**：
```json
[
  {
    "id": 1, "category_id": 1, "name": "宫保鸡丁", "price": "28.00",
    "image_url": "", "description": "经典川菜，鸡肉嫩滑，花生香脆",
    "spiciness": 3, "is_recommend": 1, "stock": 999
  }
]
```
- **说明**：
  - **只返回已上架菜品**（`dishes.is_on_sale = 1`）。下架由管理后台控制，下架菜品对小程序端完全不可见。
  - **库存为 0 的菜品仍会返回**，前端显示「已售完」—— 让顾客知道这道菜存在、只是暂时没有，比整条消失更合理。
  - `is_on_sale` 是运营概念，**不在返回值里**，小程序端没有任何场景需要它。
  - `price` 在本接口是字符串（直接来自数据库 DECIMAL），前端按原样展示即可。
- **搜索行为**：
  - **同时匹配菜名与描述**。只搜菜名会漏掉「辣」这类只在描述里出现的词 ——
    菜品名里没有「辣」字，但好几道菜的描述是「麻辣鲜香」。
  - **菜名命中的排在前面**。搜「汤」时「番茄蛋汤」应当比「描述里顺带提到汤」的菜更靠前，
    否则最相关的结果可能藏在后面。实测搜「辣」的顺序：
    `酸辣汤（菜名命中）/ 麻婆豆腐 / 鱼香肉丝 / 口水鸡 / 凉拌木耳（描述命中）`
  - 关键词里的 `%` 与 `_` 会按**字面**匹配（已做 LIKE 转义）：
    搜 `%` 时返回 0 条结果。转义实现在 `DB::likeEscape()`。
  - 首尾空格会被裁掉；搜不到时返回**空数组**。

> 「哪些菜算在售」这条规则（以及「推荐场景要额外排除已售完」那条）统一定义在
> `core/DishRepo.php`。此前它散落在 6 个地方并且已经不一致 ——
> 详见 [architecture.md](architecture.md) 第 13 节。

### 3. 获取菜品详情

- **地址**：`GET /api/dish/detail.php?id=3`
- **鉴权**：免登录（与菜品列表一致）
- **入参**：`id`（菜品ID，必填）
- **返回 data**：
```json
{
  "id": 3,
  "category_id": 1,
  "name": "糖醋里脊",
  "price": 32,
  "image_url": "https://...",
  "description": "酸甜可口，外酥里嫩",
  "spiciness": 0,
  "is_recommend": 1,
  "stock": 999,
  "category_name": "热菜",
  "sold": 12
}
```
- **字段说明**：
  - `category_name`：所属分类名（列表页按分类分组展示，不需要它）
  - `sold`：累计售出份数 = 该菜品在所有**未取消**订单中的数量之和（订单状态 3 不计入）
  - `price` 为数字类型，前端负责格式化成两位小数显示
- **错误**：
  - `400` 缺少或非法 `id`
  - `404` 菜品不存在 **或已下架**（下架菜品一律按不存在处理，避免顾客从旧链接继续下单）

### 4. 获取购物车列表 🔒

- **地址**：`GET /api/cart/list.php`
- **请求头**：`token: <令牌>`
- **入参**：无（用户身份由令牌决定）
- **返回 data**：
```json
[
  { "cart_id": 3, "quantity": 2, "dish_id": 1, "name": "宫保鸡丁",
    "price": "28.00", "image_url": "", "description": "经典川菜，鸡肉嫩滑，花生香脆" }
]
```

### 5. 加入购物车 🔒

- **地址**：`POST /api/cart/add.php`
- **请求头**：`token: <令牌>`
- **入参**：`{"dish_id": 3, "quantity": 2}`（quantity 默认 1）
- **返回 data**：`null`，msg 为「已加入购物车」
- **说明**：购物车已有该菜品则累加数量，否则新增记录。
- **错误**：
  - `400` 缺少 `dish_id`，或菜品不存在
  - `409` 菜品已下架（正常入口看不到下架菜品，但可能是**加购之后**后台才下架的）

### 6. 移除购物车商品 🔒

- **地址**：`POST /api/cart/remove.php`
- **请求头**：`token: <令牌>`
- **入参**：`{"cart_id": 5}`
- **返回 data**：`null`，msg 为「已移除」
- **说明**：后端同时校验 `cart_id` 与当前用户，删除他人记录返回 `404`。

### 7. 调整购物车数量 🔒（新增）

- **地址**：`POST /api/cart/update.php`
- **请求头**：`token: <令牌>`
- **入参**：`{"cart_id": 5, "quantity": 3}`
- **返回 data**：

```json
{ "cart_id": 5, "quantity": 3, "removed": false }
```

- **语义**：**绝对设置**：`quantity` 为设置后的最终数量。
  因此接口是**幂等**的：同一请求重试多次结果一致，不会因为网络重试而多加一次。
- **数量为 0**：表示**移除**该条记录，返回 `{"quantity":0,"removed":true}`（前端会先弹窗确认）。
- **错误**：
  - `cart_id` / `quantity` 缺失、非数字、负数、大于 999 → `400`
  - 记录不存在**或不属于当前用户** → `404`（两种情况返回同一个 404，避免被用来枚举他人数据）
- **说明**：不校验库存上限，与 `cart/add.php` 保持一致（库存统一在 `order/create.php` 下单时校验）。
- **实现提示**：MySQL 的 `UPDATE` 在「新值与旧值相同」时受影响行数也是 0，
  所以不能仅凭受影响行数判断记录是否存在，否则"把数量设成原值"会误报 404。

### 8. 创建订单（结算下单）🔒

- **地址**：`POST /api/order/create.php`
- **请求头**：`token: <令牌>`
- **入参**：`{"remark": "少放辣"}`
- **返回 data**：
```json
{ "order_id": 10, "order_no": "202401011200001234", "total_price": "56.00", "status": 0 }
```
- **说明**：在事务内锁定当前用户的购物车 → 读取明细并计算总价 → 写入 `orders` + `order_items`
  → **原子扣减库存**（`UPDATE dishes SET stock = stock - ? WHERE id = ? AND stock >= ?`）
  → 清空购物车 → 提交。任一环节失败自动回滚。新订单状态为 `0`（待支付）。
- **防超卖**：库存的「检查」与「扣减」合并为一条原子 SQL（条件写在 WHERE 里），
  并发下单时后到的请求影响行数为 0 → 回滚并返回 `409`，因此库存不会被扣成负数。
  同理，同一用户重复提交结算也只会生成一笔订单（购物车行有 `FOR UPDATE` 行锁）。

### 9. 查询我的订单 🔒

- **地址**：`GET /api/order/list.php`
- **地址**：`GET /api/order/list.php?status=2`
- **地址**：`GET /api/order/list.php?page=2&per_page=10`
- **请求头**：`token: <令牌>`
- **入参**：

  | 参数 | 必填 | 说明 |
  | --- | --- | --- |
  | `status` | 否 | `0` 待支付 / `1` 已支付 / `2` 已完成 / `3` 已取消（**推荐**）；兼容写法 `pending` / `paid` / `completed` / `cancelled`；不传返回全部；传非法值返回 `400`（不再静默查出错误数据） |
  | `page` | 否 | 第几页，从 1 开始，默认 `1`（小于 1 会被夹到 1） |
  | `per_page` | 否 | 每页条数，默认 `10`，**上限 50**（超出会被夹到 50） |

- **返回 data**：
```json
[
  {
    "id": 10, "order_no": "202401011200001234", "total_price": "56.00",
    "status": 0, "status_text": "待支付", "remark": "少放辣",
    "created_at": "2024-01-01 12:00:00",
    "items": [ { "dish_name": "宫保鸡丁", "dish_price": "28.00", "quantity": 2, "image_url": "" } ]
  }
]
```
- **说明**：`id`、`status`、`quantity` 均返回数字类型；`status_text` 由后端返回，前端无需自己维护状态映射。
- **分页说明**：
  - 返回结构**仍然是数组**，属刻意约定 —— 前端与文档都已按数组约定，
    改成对象会波及一片。
  - 因此「还有没有下一页」由**客户端**用「本页返回条数 == `per_page`」判断
    （前端 `pages/myOrders` 就是这么做的：触底时据此决定要不要继续加载）。
  - 排序是 `created_at DESC, id DESC`。**第二个排序键是必要的**：
    只按 `created_at` 排的话，同一秒创建的两笔订单顺序不固定，
    翻页时会出现「上一页出现过、下一页又出现一次」或整条被跳过。
  - 页码超出范围时返回空数组。

### 10. 订单支付 🔒（新增）

- **地址**：`POST /api/order/pay.php`
- **请求头**：`token: <令牌>`
- **入参**：`{"order_id": 10}`
- **返回 data**：
```json
{ "order_id": 10, "order_no": "202401011200001234", "status": 1, "status_text": "已支付" }
```
- **状态流转**：`0 待支付` → `1 已支付`
- **错误**：订单不存在或不属于当前用户 → `404`；当前状态不是待支付 → `409`
- **⚠️ 重要**：当前为**模拟支付**（直接把订单标记为已支付，便于本地跑通业务流程）。
  正式上线必须替换为微信支付：本接口只负责统一下单，订单状态变更必须由**微信支付回调**驱动，并在回调中验签、做幂等处理。

### 11. 取消订单 🔒（新增）

- **地址**：`POST /api/order/cancel.php`
- **请求头**：`token: <令牌>`
- **入参**：`{"order_id": 10}`
- **返回 data**：
```json
{ "order_id": 10, "order_no": "...", "status": 3, "status_text": "已取消", "restored_items": 2 }
```
- **状态流转**：`0 待支付` 或 `1 已支付` → `3 已取消`
- **库存回滚**：按订单明细逐项恢复库存（`restored_items` 为恢复的明细条数），事务保证一致性
- **错误**：已完成/已取消的订单不可再取消 → `409`

### 12. 确认订单完成 🔒（新增）

- **地址**：`POST /api/order/complete.php`
- **请求头**：`token: <令牌>`
- **入参**：`{"order_id": 10}`
- **返回 data**：
```json
{ "order_id": 10, "order_no": "...", "status": 2, "status_text": "已完成" }
```
- **状态流转**：`1 已支付` → `2 已完成`
- **错误**：未支付订单不可直接完成 → `409`

### 13. 微信一键登录（登录即注册）

- **地址**：`POST /api/user/login.php`
- **入参**：`{"code": "wx.login 返回的临时 code", "nickname": "昵称(可选)", "avatar_url": "头像(可选)"}`
- **返回 data**：用户完整信息 + `token`
- **说明**：
  - 后端用 `code` 调微信 `code2Session` 换取 `openid`，再按 openid 查用户，**不存在则自动创建**（因此无需注册流程）。
  - `code` 由小程序端 `wx.login()` 获取，5 分钟有效且只能用一次。
  - 未配置 `config/wechat.php` 的 `appsecret` 时返回 `503`（前端提示「微信登录未配置」）。
  - code 无效或已被使用 → `401`（微信返回 40029 / 40163）。
  - **不接受客户端直接传 openid**：那会导致「知道 openid 即可登录成他人账号」。
- **本地调试通道**：同时满足「`config/security.php` 中 `allow_dev_openid_login = true`」与
  「请求来自本机回环地址」时可传 `{"openid": "..."}` 直接登录，仅供本地开发（线上必须关闭）。

### 14. 校验登录态 / 获取当前用户 🔒

- **地址**：`GET /api/user/check.php`
- **请求头**：`token: <令牌>`
- **入参**：无（**不再需要也不接受 user_id**）
- **返回 data**：当前登录用户信息；令牌无效返回 `401`，用户不存在返回 `404`

### 15. 修改个人信息 🔒

- **地址**：`POST /api/user/update.php`
- **请求头**：`token: <令牌>`
- **入参**：`{"nickname": "新昵称", "phone": "138xxxx", "address": "收货地址"}`
- **返回 data**：更新后的用户信息
- **说明**：只能修改自己的信息；手机号会做格式与唯一性校验（与他人冲突返回 `409`）。

### 16. AI 智能问答（含推荐菜品提取）

- **地址**：`POST /api/ai/chat.php`
- **入参**：`{"message": "推荐几道辣菜", "history": [{"role":"user","content":"..."}]}`
- **`history` 的处理**：服务端会清洗并裁剪（见 `DeepSeek::sanitizeHistory()`）——
  **只放行 `user` / `assistant` 角色，丢弃 `system`**（否则可注入系统级指令覆盖助手身份），
  并限制条数 12 / 单条 1000 字 / 合计 4000 字。前端也会只带最近 12 条，
  但那只是省流量，服务端这一层才是边界。
- **返回 data**：
```json
{
  "reply": "为您推荐麻婆豆腐，麻辣鲜香很下饭~",
  "recommend_dishes": [ { "id": 2, "name": "麻婆豆腐", "ai_reason": "麻辣鲜香" } ],
  "has_recommend": true
}
```
- **说明**：先让 AI 正常回答，然后**从 AI 的回复文本里识别它提到的菜品**，把这些菜品作为可点击卡片返回
  （`ai_reason` 取菜品名后面的那句话，**以下一个菜名或句末标点为界**）。这样做的好处：
  1. **不会漏**：用户说「我有点渴」「西瓜汁」这类不含关键词的消息，只要 AI 回复里提到了菜品名，就有对应卡片；
  2. **更准确**：卡片对应 AI 回复中提到的菜品；
  3. **更省钱**：绝大多数情况不需要第二次调用 AI。

  只有当「回复里一道菜都没提到、而用户又明显在要推荐」时，才兜底调用一次
  `DeepSeek::recommend()` 获取结构化推荐（此处会多一次 AI 调用）。
  最多返回 4 张卡片，顺序与 AI 描述顺序一致。对应前端「AI 助手」页面。

  > 文本解析逻辑独立在 `backend/core/AiReply.php`（纯文本处理、不依赖数据库，可单独单元测试）。
  > 支持三种回复格式：① 每道菜一行「- 菜名：理由」；② 一行内用括号/顿号并列多道菜；③ 一句话顺带提到。
  > 其中格式 ② 曾出现「第一道菜的理由把后面几道菜一起吞掉」的问题，修复方式是把理由的结束位置
  > 限定在「下一道菜名的起点」，详见该文件头部注释。

### 17. AI 智能问答 · 流式版（SSE）

- **地址**：`POST /api/ai/chat_stream.php`
- **入参**：与 `ai/chat.php` 完全一致（`message` + 可选 `history`）
- **响应**：`Content-Type: text/event-stream`，按 SSE 逐段推送（不使用 `{code,msg,data}` 包裹）
- **事件格式**：每个事件是一行 `data: <JSON>`，以**空行**结束

```
data: {"type":"delta","text":"宫保"}        ← 增量文本，一次回复会来很多条
data: {"type":"delta","text":"鸡丁"}
data: {"type":"done","reply":"宫保鸡丁…","recommend_dishes":[…],"has_recommend":true}
data: [DONE]                                ← 结束标记（与 OpenAI 风格一致）
```

- **事件类型**：
  | type | 含义 | 字段 |
  | --- | --- | --- |
  | `delta` | 一段增量文本 | `text` |
  | `done` | 全部结束 | `reply`（完整回复）、`recommend_dishes`、`has_recommend` |
  | `error` | 出错（此后不会再有内容） | `msg` |
- **为什么推荐卡片只放在 `done` 里**：卡片是从**完整回复**里识别菜名得到的
  （见 `core/AiReply.php`），增量阶段拿不到全文，所以只让 `delta` 负责"显示得快"。
- **连接保活**：连接建立后会先发一行 `: connected`（以冒号开头，SSE 里是注释，客户端应忽略），
  让客户端尽早拿到响应头、把「正在输入」状态显示出来。
- **`[DONE]` 之后**：服务端直接结束响应，连接关闭。
- **出错时**：因为已经进入流式输出，无法再返回 JSON 错误码，只能发 `error` 事件。
  唯一的例外是**限流**与**参数校验**——它们发生在切换成 SSE 之前，仍返回普通 JSON（见下节）。
- **对应前端**：`frontend/utils/sse.ts`（`wx.request` + `enableChunked` + `onChunkReceived`）。
  基础库 < 2.20.2 时前端会自动回退到非流式的 `ai/chat.php`。

## AI 接口限流

`ai/chat.php`、`ai/chat_stream.php` 两个接口每次调用都会**真实消耗
DeepSeek 额度**，因此都经过统一限流（`backend/core/AiRateLimit.php`）。

**三层同时生效**：

| 层 | 标识 | 默认限额 | 作用 |
| --- | --- | --- | --- |
| 每分钟 | 身份 | 登录用户 6 次 / 游客 3 次 | 挡住瞬时连点与脚本高速轰炸 |
| 每天 | 身份 | 登录用户 100 次 / 游客 30 次 | 挡住「细水长流」式的持续消耗 |
| 每天 | 全站 | 3000 次 | 最后一道保险：无论怎么绕过前两层，当天总消耗都有上限 |

**身份怎么判定**：带了有效登录令牌就按用户ID（`uid:10004`），否则按 IP（`ip:1.2.3.4`）。
这三个接口本身免登录，所以游客也能用 AI，只是额度更低。

**超限时**返回：

```
HTTP/1.1 200（本项目统一用 200 包壳，业务码在 body 里）
Retry-After: 37

{ "code": 429, "msg": "请求太频繁了，请稍等一会儿再问", "data": null }
```

**成功时**会带上剩余额度，便于前端提前提醒：

```
X-RateLimit-Limit-Minute: 6
X-RateLimit-Remaining-Minute: 5
X-RateLimit-Limit-Day: 100
X-RateLimit-Remaining-Day: 99
```

> 限额常量在 `core/AiRateLimit.php` 顶部，改限额不需要动数据库。
> 三个接口共用同一套额度 —— 它们烧的是同一份 API 额度，分开计数等于给了双倍配额。
